# ctx-builder — Context Builder Agent

AI-агент для автоматического сбора и формирования релевантного контекста проекта для AI-систем (Claude Code, OpenAI Codex, локальные LLM).

**Главная задача:** дать AI ровно тот контекст, который нужен для конкретной задачи — не больше, не меньше.

## Возможности

| Use Case | Что собирает |
|----------|-------------|
| **Code Review** | Архитектурный контекст, связанные классы, project rules |
| **Code Generation** | Похожие реализации, conventions, patterns, примеры кода |
| **Refactoring** | Зависимости, call graph, затронутые модули |
| **Bug Fixing** | Контекст stacktrace, цепочка вызовов, связанные сервисы |
| **Documentation** | Описания модулей, структура архитектуры, API контракты |
| **Architecture Analysis** | Слои, модули, паттерны, связи между компонентами |

## Поддерживаемые технологии

| Стек | Язык | Парсер | Охват |
|------|------|--------|-------|
| ASP.NET Core | C# | Roslyn AST | ~100% |
| Unity | C# | Roslyn + .meta analysis | ~97% |
| Laravel | PHP | PHP Parser | ~85% |
| Flutter | Dart | Dart Analyzer | ~87% |
| Node.js / TypeScript | TS/Vue | TS Compiler API + regex | ~20% |
| Unreal Engine | C++ | tree-sitter AST | ~49% |

Для языков без парсера (Rust, Go, Python) агент работает через прямое чтение файлов через `read_file`/`compact_file`.

## Настройка

### 1. API ключи

Скопируйте шаблон и заполните хотя бы один ключ:

```bash
cp .env.example .env
# Отредактируйте .env — вставьте свой API ключ
```

Минимально нужен один ключ. Рекомендуется DeepSeek (`DEEPSEEK_API_KEY`) — лучший баланс цены и качества.

### 2. Выбор модели по умолчанию

Модель можно задать тремя способами (в порядке приоритета):

**Способ 1 — `.ai-context.yml` (на конкретный проект):**
```yaml
model:
  provider: openai
  name: gpt-4o
```

**Способ 2 — переменные окружения (глобально):**
```bash
# В .env или экспортом
CTX_BUILDER_DEFAULT_PROVIDER=deepseek
CTX_BUILDER_DEFAULT_MODEL=deepseek-v4-flash
```

**Способ 3 — флаг CLI (на один запуск):**
```bash
ctx-build -p . -t "Code Review" --provider anthropic --model claude-haiku-4-5-20251001
```

Если ничего не указано — используется `deepseek/deepseek-chat`.

### 3. Проверка установки

```bash
ctx-build -p . -t "test"
```

## Быстрый старт

```bash
# Базовое использование
ctx-build -p /path/to/project -t "Code Review: Analyze architecture"

# Выбор модели
ctx-build -p . -t "Refactoring: Extract auth module" --provider openai --model gpt-4o
ctx-build -p . -t "Bug Fixing: NullPointer in UserService" --provider anthropic --model claude-opus-4-7
ctx-build -p . -t "Code Generation: Add email verification" --provider deepseek --model deepseek-v4-pro

# Локальная модель (Ollama, LM Studio, vLLM)
export LOCAL_LLM_URL=http://localhost:11434/v1
ctx-build -p . -t "review" --provider local --model llama3

# Сохранить в файл
ctx-build -p . -t "Documentation: API overview" -o docs/context.md
```

| Провайдер | Флаг | Модели | Переменная |
|-----------|------|--------|-----------|
| OpenAI | `--provider openai` | gpt-4o, gpt-4-turbo | `OPENAI_API_KEY` |
| Anthropic | `--provider anthropic` | claude-opus-4-7, claude-sonnet-4-6 | `ANTHROPIC_API_KEY` |
| DeepSeek | `--provider deepseek` | deepseek-chat, deepseek-v4-pro | `DEEPSEEK_API_KEY` |
| Локальный | `--provider local` | Любая OpenAI-совместимая | `LOCAL_LLM_URL` |

**Рекомендация:** deepseek-v4-flash — лучший баланс цены и скорости для plan+execute архитектуры. deepseek-v4-pro даёт более детальный вывод, но в 3-4 раза медленнее.

## Формат вывода — 8 секций

```
1. PROJECT SUMMARY      — стек, размер, тип проекта (2-4 предложения)
2. ARCHITECTURE         — паттерн (Layered/DDD/ECS/Modular Monolith), слои, ответственности
3. RELATED FILES        — 5-8 файлов с путём, типом, назначением, релевантностью
4. DEPENDENCY GRAPH     — импорты/импортируется, граф вызовов (из get_dependencies)
5. CONVENTIONS          — naming rules, patterns, code style (project-specific)
6. SIMILAR IMPLEMENTATIONS — 3-4 класса/файла с теми же паттернами
7. TASK CONTEXT         — что трогать, чему следовать, чего избегать
8. RELEVANT CODE SNIPPETS  — 3-5 сниппетов из read_file/compact_file (только реальный код)
```

## Конфигурация — `.ai-context.yml`

Создайте `.ai-context.yml` в корне целевого проекта:

```yaml
architecture:
  auto_detect: true

indexing:
  exclude:
    - node_modules/**
    - .git/**
    - Binaries/**
    - "*.generated.*"

context:
  max_tokens: 120000          # лимит выходного документа
  agent_token_budget: 80000   # бюджет на сбор данных (pre-collect + planner)
  include_tests: true
  include_docs: true

similarity:
  enabled: true

model:
  provider: deepseek
  name: deepseek-v4-pro
```

Если `.ai-context.yml` отсутствует — используются значения по умолчанию (те же, что в примере).

## Архитектура агента

Агент решает одну задачу: по текстовому описанию и пути к проекту собрать AI-оптимизированный контекстный документ из 8 секций. На входе — промпт пользователя и папка с исходниками. На выходе — структурированный документ с суммаризацией проекта, архитектурой, релевантными файлами, графом зависимостей, конвенциями, похожими реализациями, рекомендациями и сниппетами кода.

```
CLI (cli.py)              MCP Server (mcp_server.py)
         └────────────┬────────────┘
                   Agent (agent.py)
              Plan+Execute pattern
         ┌─────────┴──────────┐
    Phase 0+2 (код)      Phase 1 (LLM)      Phase 3 (LLM)
    Pre-collect +        Planner             Writer
    Execute              JSON-план тулзов    пишет документ
         │                    │
    Tools (tools.py)     Prompts (prompts/system.py)
    15 тулзов +           planner/writer промпты
    mask_secrets
         │
    Index (index.py)
    ProjectIndex, DependencyGraph, SQLite cache
         │
    ┌────┴─────────────┐
  Scanner           Parsers (parsers/)
  scanner.py        csharp, php, typescript, dart, cpp, unity
  RepoIndex,
  RepoScanner
         │
    Config (config.py)    GitLab (gitlab.py)
    .ai-context.yml       GitLabClient, MR анализ
```

### Принцип работы

Агент работает в три фазы: **Pre-collect → Plan → Write**. Между фазами нет обратной связи — планировщик принимает решение один раз, все инструменты второй фазы вызываются параллельно.

### Фаза 0: Pre-collect

Цель — собрать базовый срез проекта, не зная задачи.

Четыре обязательных инструмента вызываются всегда и параллельно:

- **get_summary** — сколько файлов, какие языки, сколько классов/методов/зависимостей.
- **get_docs** — читает README, ARCHITECTURE.md и прочие документы проекта. Даёт человеческое описание того, что это за проект.
- **classify_entities** — раскладывает все исходные файлы по типам сущностей: контроллеры, сервисы, репозитории, middleware, валидаторы, DTO. Считает долю неклассифицированных файлов — если их больше половины, writer честно предупреждает о низком качестве архитектурного анализа.
- **get_module_graph** — строит граф зависимостей между директориями верхнего уровня: кто кого импортирует.

Параллельно с ними вызывается **search_symbol** — поиск символов (классов, методов, функций) по ключевым словам. Чтобы извлечь ключевые слова из задачи, используется мини-вызов LLM: модель получает промпт «извлеки до 8 поисковых терминов, верни JSON-массив» и возвращает конкретные технические термины. Для страховки результат всегда дополняется словами, извлечёнными регулярным выражением из текста задачи — если LLM вернул общие слова, regex-подстраховка добавит пропущенные конкретные термины.

Для каждого ключевого слова вызывается search_symbol. Он ищет по именам классов, методов, функций — case-insensitive, частичное совпадение. Каждый результат содержит имя символа, тип, параметры и путь к файлу.

### Фаза 1: Plan

Цель — понять, какие конкретно файлы нужно прочитать для ответа на задачу.

Планировщик — один вызов LLM. Получает промпт с описанием доступных инструментов и всеми pre-collected данными. Возвращает JSON-план: какие инструменты вызвать и с какими параметрами.

Доступные инструменты: **sample_signatures** (случайная выборка сигнатур для анализа конвенций), **get_dependencies** (граф импортов для указанных файлов), **compact_file** (сжатое представление — только сигнатуры), **read_file** (полное чтение с номерами строк), **search_symbol** (дополнительные поиски), **find_files** (поиск по паттерну имени), **find_similar** (похожие классы).

Ключевые правила в промпте планировщика: обязательность get_dependencies и sample_signatures, проверка покрытия (если pre-collected search_symbol не релевантен задаче — запросить дополнительные поиски), и выбор primary file для read_file (файл, реализующий концепт задачи, а не инфраструктурный middleware).

Результат парсится как JSON. Если не указан get_dependencies — срабатывает fallback: из результатов search_symbol извлекаются все упомянутые пути к файлам, ранжируются по частоте, и топ-файлы подставляются автоматически. К выбору планировщика всегда добавляются топ-файлы из search_symbol — страховка на случай, если планировщик выбрал файлы с пустым графом зависимостей.

### Фаза 2: Execute

Все инструменты из JSON-плана вызываются параллельно. Никаких LLM-вызовов — чистый сбор данных. Результаты склеиваются с pre-collected данными.

Каждый инструмент учитывает токен-бюджет. read_file предлагает сначала использовать compact_file для больших файлов. compact_file запоминает, какие файлы уже сжаты. Все инструменты маскируют секреты (API-ключи, токены, приватные ключи, пароли) в выводе.

### Фаза 3: Write

Финальный вызов LLM. На входе — все собранные данные, задача пользователя, и жёсткая структура из 8 секций. Writer не имеет доступа к инструментам — только пишет документ на основе собранного.

Ключевое правило: использовать только данные из инструментов. Никаких знаний фреймворков или языков из памяти модели. Если инструмент не дал данных — честно сообщить, а не заполнять пробелы выдумкой. Для секции с зависимостями различаются две ситуации: «планировщик не запросил get_dependencies» и «запросил, но данные пустые» — во втором случае writer объясняет, что импорты могут быть внешними пакетами или framework-заголовками.

### Ключевые архитектурные решения

**Plan-and-Execute вместо agent loop.** Изначально был gatherer-агент с циклом в 7-30 итераций — LLM решал, какой инструмент вызвать следующим. Это было медленно, дорого и нестабильно. Теперь один планировщик принимает все решения сразу, исполнение параллельное. Всегда ровно 1 шаг LLM в фазе сбора данных.

**Параллельное выполнение.** В каждой фазе все независимые вызовы делаются одновременно: 4 обязательных инструмента + N поисков по ключевым словам в фазе 0; все запланированные чтения/сжатия/зависимости в фазе 2.

**Токен-бюджет и дедупликация.** Каждый вызов read_file или compact_file учитывает потраченные токены. Повторное чтение одного диапазона строк детектится и пропускается. Большие файлы предлагается сначала сжать.

**Индекс как разделяемый кеш.** Результаты парсинга (AST, граф зависимостей) сохраняются в SQLite рядом с проектом. При повторном запуске для того же проекта парсинг не повторяется — только если изменились исходники. Холодный старт: полное сканирование + AST-парсинг (1-58 сек). Горячий старт: загрузка из кеша (<1 сек).

**Универсальность без хардкода.** Агент не знает о конкретных языках, фреймворках или паттернах. Ключевые слова извлекаются LLM с regex-подстраховкой, а не фиксированным списком доменных терминов. Резолвер импортов ищет tsconfig в поддиректориях и делает fuzzy-поиск по всей файловой системе, а не только по фиксированным путям. Промпты не содержат примеров под конкретные юзкейсы.

**Безопасность.** Секреты маскируются при чтении файлов (API-ключи, JWT-токены, приватные ключи, connection strings). Из индексации исключены `.env`, `*.pem`, `*.key`, и любые файлы с `secret`/`credential`/`private_key` в имени.

## SQLite кеш

Индекс сохраняется в `.ai-context.db` (SQLite, 6 таблиц): `meta`, `files`, `classes`, `methods`, `deps`, `calls`.

- **Холодный старт** (первый запуск): полное сканирование + AST-парсинг (1-58 сек в зависимости от размера)
- **Горячий старт** (без изменений): загрузка из кеша (<1 сек)
- **Инкремент** (есть изменения): перепарсинг только изменённых файлов
- **ctx_build (холодный):** ~20s (индекс + 1 LLM-планер + 1 LLM-райтер + параллельный execute)
- **ctx_build (горячий):** ~18s (<1s индекс + 1 LLM-планер + 1 LLM-райтер + параллельный execute)
